1. Bounding-box detection

Bbox detection is the foundation: it tells every downstream check which characters and props are where. Implementation: server/lib/entityConsistency.js + Python cascade detector.

Two-pass flow

  1. Pass 1 — Gemini 2.5 Flash runs the prompt in prompts/bounding-box-detection.txt and returns figures with bbox: [ymin, xmin, ymax, xmax] normalised 0-1.
  2. Pass 2 (refine) — Cascade face detector (Python anime + Haar) runs on the same image; results merged with Gemini bboxes. Catches faces Gemini missed.
  3. Object name canonicalisation — detected names mapped back to Visual Bible IDs (e.g. "the wooden bow" → ART012).

Persistence

Bbox results land on sceneImage.bboxDetection per page. Not shared across versions: each round of repair runs fresh detection on the new image. Reusing sharedBboxDetection across rounds caused a long-running bug where v3's bbox showed v0's figures.

2. Four evaluators, one consolidator

Run in parallel after image generation. None of them returns a score — since b9658b501 they report defects and the score is derived from the defects (§3).

EvaluatorSees the image?OutputPrompt
Qualityyesfixable_issues[], coherence_gate, verdictimage-evaluation.txt
Prompt complianceno — stage 2 of the three-stage call, judges a stage-1 vision inventory against the promptfixable_issues[], figures[]image-prompt-compliance.txt
Semanticyesfixable_issues[] — does the image tell the story beatimage-semantic.txt
Entityyes (cross-page grid)fixable_issues[] + cells / pagesToFix / garment / expectedColourentity-consistency-check.txt

One issue shape across all four (2026-08-08): every finding is { type, severity, character, description, fix } inside fixable_issues[]. Parsers still accept the legacy names (semantic_issues, issues, problem, fixInstruction) so stored evaluations keep reading.

type comes from a closed list owned by server/lib/evalBuckets.js, which maps it to a bucket and a repair method. Unknown types land in other — tracked, never silently dropped. normalizeType() splits the compound values models invent (clothing_and_hair). Note hair → character_identity, not clothing: the clothing repair repaints a garment and cannot fix a ponytail. 99% of raw findings route to a real bucket.

The consolidator is the scoring source. prompts/feedback-consolidator.txt merges all four into deduped_issues[], and that list is what scoring.js charges — an important trap: category work on the four evaluator prompts is worthless until it survives the consolidator (it did not, until 994cb85e1).

Evaluators are tolerant by design: pose mirror (left/right body-part swap), minor framing nits, and aesthetic preferences don't deduct. Style rules are style-conditional — neon is not a defect in a cyber story and is one in a watercolour story — so the art style must be passed in, resolved via resolveEvalArtStyle() so the Lab and staging always match. The decision log records which deductions were rejected and why.

3. The unified score

One number drives every redo decision, and it is only the defect list:

finalScore = 100 − Σ SEVERITY_POINTS[issue.severity]
SeverityDeduction
CATASTROPHIC−50
CRITICAL−25
MAJOR−15
MODERATE−5
MINOR−2

No floor. A negative finalScore means the evaluators exceeded 100 points of penalty, and admin surfaces show it (−10, −140) rather than a wall of zeros that hides how bad a page is. There is exactly one score per version — do not add a second, differently-clamped copy.

Zero-point types. ZERO_POINT_TYPES in scoring.js currently holds garment_colour: it is corrected mechanically (masked L*a*b* match toward the character's canonical colour), so charging it would trip the redo gate over a hue shift. It is still a first-class category so it appears in per-category stats instead of hiding on a private channel.

Severity is the median of the evaluators' own votes

~76% of issues are flagged by a single evaluator, and one evaluator shouting CRITICAL was costing 25 points. The consolidator records each evaluator's own severity per merged defect (severities: {"quality":"MAJOR","semantic":"CRITICAL"}) and medianSeverity() in feedbackConsolidator.js derives the value in code: one vote → that vote; two → the lower; three or more → the middle. The model's own pick is kept as severityChosen so the gap stays auditable. Three attempts to do this inside the prompt all failed — see the 2026-08-09 decision entry before re-litigating.

4. Repair workflow loop

⚠ The repair method called inpaint does not inpaint. inpaintPage() builds a text instruction from the findings and sends the whole image to editImageWithPrompt() → Grok/Gemini, which returns a whole new image. There is no mask and nothing is preserved — composition, other characters, background and style can all drift. True masked inpainting (unmasked pixels survive byte-for-byte) lives in server/lib/imageInpainting.js and was never wired in; it is marked dead code. Do not reason about "blast radius" or skip a re-evaluation on the assumption that only a region changed.

Measured repair outcomes (56 attempts, 4 stories, 2026-08-11) — every method is net-negative, and 55% of attempts produce a version pick-best discards:

methodattemptsbetterworseavg pts

Caveat: the score itself has variance (identical input has returned −70 four times and −20 once), so small deltas are noise. The −18 average on scale-repair is not.

Triggered by RepairWorkflowPanel → useRepairWorkflow.runFullWorkflow(). Up to maxPasses = 3 global passes:

Pass 1:
  EVALUATE ALL pages          (quality + semantic + entity-from-generation)
  IDENTIFY BAD PAGES          (score < 60 OR issues >= 5)
  REDO bad pages once each    (POST /:id/iterate/:pageNum)

Pass 2..3:
  RUN ENTITY CONSISTENCY      (fresh bbox on new images)
  EVALUATE ALL pages          (with fresh entity data)
  IDENTIFY BAD PAGES
  REDO bad pages once each

FINAL:
  ENTITY CONSISTENCY (last)
  EVALUATE ALL (final)
  CHARACTER REPAIR (max 3 pages, critical first, Grok blended)
  PICK BEST VERSIONS

Thresholds in server/config/models.js → REPAIR_DEFAULTS:

scoreThreshold60 — pages below this get redone
issueThreshold5 — pages with 5+ fixable issues get redone
maxPasses3 — global passes
maxCharRepairPages20 — max pages for char repair per run
The threshold dropped from 80 → 60 to stop redoing pages with cumulative-but-minor issues. Three checks each deducting 5 points used to trigger a costly redo for what was actually a fine image.

5. Character repair

When entity consistency flags a character mismatch (wrong hair, wrong outfit, wrong age), character repair fixes only that character, preserving the background. Three modes (server/lib/images.js → repairCharacterMismatchWithGrok):

ModeHowCostWhen
Cutout (default)Extract bbox + 20% padding → send cutout + avatar to Grok → composite back with feathered edge (~8% of smaller dimension).$0.02Background untouched. Default for body / outfit fixes.
BlendedBlur character region → Grok regenerates → 30px feathered blend onto bbox + 50% padding.$0.02Face-only repairs.
BlackoutFull scene with blackout overlay → Grok regenerates entire scene.$0.02Background and character both wrong.

Preset-aligned cutout

computePresetAlignedExtract() picks one of Grok's 13 aspect presets and grows one axis to match — no letterbox padding, just more scene context.

6. Scale repair

Separate from character repair. Used when a character is correctly rendered but in the wrong place / wrong size (e.g. should be a small figure in the background, drawn as foreground). server/lib/scaleRepair.js.

Prompt is framed as MOVE / RELOCATE, not ADD: "every named character is already drawn somewhere in the input image — do not add new figures; find the existing figure of [visual identifier] and MOVE+SHRINK it to the target position [metadata position]". Repaints the abandoned area. No name leakage (uses visual identifiers, not character names).

7. Pick-best version selection

After all repair passes finish, every page has 1..N versions stored under imageVersions[]. POST /:id/repair-workflow/pick-best-versions activates the highest-scoring version per page. Character-repair outputs are also versions, so they compete with the original + redo attempts.
