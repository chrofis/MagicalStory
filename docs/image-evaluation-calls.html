Image evaluation — every call, what it sees, how it consolidates

One scene page, from generated pixels to a final score. Five model calls run inside evaluateImageQuality, plus a local detection before it and one story-level pass after. The split that matters throughout: some callers see the prompt (they know who is supposed to be there) and some are blind (they only see the picture).

Who names the figures

This is the part that keeps biting, so it is worth stating on its own. Three of the calls produce a figure list, but only two are allowed to attach a name to a figure:

① Quality evaluatorhas the reference photos, the character descriptions, the clothing contract and each character's declared position owns matches[] — identity + boxes
⓪ Figure detectionhas the per-character identity lines and full-body masks owns its own names — independent second opinion
↓ compared on body-box centres · identityAgreement.js
They agreethe page was easy — carry on
They disagreethe detector wins (it has masks and clothing lines); the page is harvested into the Lab set Identity conflicts (auto-harvested)

The two blind calls — ② and ④ — describe figures but never name them. They have no character contract, so a name from them would be a guess. ④ gives each figure a descriptive label ("the young boy in green") and Stage 2 resolves that label to a real name by pairing on zone against ①'s matches[].

Why it must work that way. Until 2026-08-23, P1 (②) was handed the reference photos and asked to match. It answered UNMATCHED at confidence 0 — and because that array is not empty, it replaced the evaluator's real names. Measured across two production stories: 12 versions where the evaluator had named everyone at 0.85–0.90 stored unmatched instead. Every per-character check — clothing, action, scale — keys off a name, so all of them went silent on those pages.

How it consolidates

fixable_issuescall ① + call ⑤, concatenated
↓
visual score recomputedfrom the merged list, same severity rubric — not the score call ① first reported
↓
− semantic penaltycall ③ · CRITICAL −30, MAJOR −20, else −10
− entity penaltycall ⑥ · capped; raw kept as entityPenaltyRaw
↓
finalScoredrives redo, repair targeting and pick-best across versions
visualScore = 10 × max(0, 10 − Σ severityPenalty(merged fixable_issues))
finalScore = visualScore − semanticPenalty − entityPenalty

The recompute step exists because three-stage findings used to appear in the dev panel but never move the number that triggers a repair — a page sat at 85 with −30 of real defects listed under it and was never redone.

Score names, which are counterintuitive on purpose

  • qualityScore — the RAW visual score from call ①, before any penalty
  • score — the FINAL penalised score (visual − semantic − entity − three-stage)
  • semanticScore / threeStageScore — those judges' own 0–100, kept separate

Honest assessment of the complexity

Five model calls per page, from three vendors, is a lot — and the redundancy is real:

  • Three figure inventories per page (①, ②, ④). ①'s schema is a superset of ②'s, and ④'s is richer than both. ② is the odd one out: since it stopped naming anyone, its only unique output is the rendering booleans.
  • Four sources of findings (①, ③, ⑤, ⑥), each with its own severity scale, merged by concatenation and then re-scored.
  • One call's entire text output is thrown away — ②'s scene_summary and main_action are generated on every page and never returned by runVisualInventory.

The blind/sighted split is worth keeping — it is what makes a wrong-outfit or wrong-person defect detectable at all. Having two blind describers and three figure lists is not.
